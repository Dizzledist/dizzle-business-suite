## What the public Zoho contract establishes

| Area | Verified in documentation and design impact |
|---|---|
| List and detail | GET /invoices and GET /invoices/{invoice_id} are documented with ZohoInventory.invoices.READ. List enumerates IDs. Detail provides sub_total, total, balance, status, currency, customer ID, salesperson ID/name, invoice date, creation/update fields and is_emailed. Original subtotal and salesperson at send time may differ from today's detail. |
| Settlement | Invoice detail can include payment_made, credits_applied and write_off_amount. Separate read endpoints expose applied payments and credits. These are candidates for future settlement verification. A zero balance, source paid label, or comparison to subtotal alone does not establish fully paid under an agreed credit/refund policy. |
| History | GET /invoices/{invoice_id}/comments uses the same read scope. The schema includes a history item ID, optional invoice link, comment type, operation type, date and time. The example operation is generic. The contract does not guarantee a successful-send code, timezone, delivery semantics, historical retention, coverage of every send path or access to the original invoice revision. |
| Mail and audit | Zoho's System Mails report documents automated mail dates and types, including invoice notices and reminders. Audit Trail documents actions and times. Check availability of exact IDs, precision, export, historical depth and manual/bulk coverage in an approved sandbox. Email content retrieval and Mark as sent are distinct operations. |
| Pagination and incremental | The pagination guide documents page, per_page and page_context.has_more_page. The v1 invoice list exposes last_modified_time in returned fields. I found no documented reliable incremental cursor for this invoice list. Use changed-ID hints with current detail reads and bounded reconciliation until a supported cursor or delta filter is proven. Date filters are invoice dates, separate from first-send dates. |
| OAuth and organization | Region-aware Zoho API hosts, organization_id, and Zoho-oauthtoken headers are documented. Access tokens expire and can be refreshed on the server. Choose the accounts host and API host from the verified data center and use the invoice read scope. The invoices reference uses /inventory/v1 while the introduction also shows a /v3 example. Verify the actual supported route for Dizzle's approved tenant before wiring transport. |
| Throttling | The introduction lists 100 requests/minute per organization, plan-specific daily and concurrency limits, and 429 on rate limiting. Reconcile with the approved plan budget before scheduling. |
| Webhooks | Inventory workflows can issue webhooks. A status-triggered workflow can run when an invoice is marked sent. Delivery of a workflow webhook alone does not prove a successful invoice email. Validate event authentication, available triggers, and scope before adding ingress. |

## Adapter and access boundary

- The TypeScript reader is server-only and requires an injected HTTP transport and access-token supplier. The repository supplies only test mocks. It constructs GET requests for invoice pages, details, and history on allowlisted Zoho regional hosts, with explicit organization scope, redirect denial and a request timeout. It reads validated payloads and retains only the normalized fields needed for reconciliation. It does not read invoice payment links, email bodies, free-text comments or arbitrary endpoints.
- An unauthorized response can request one forced token refresh from the supplier. Other auth failures return a redacted category. Transient and 429 failures use bounded retry with backoff and honor Retry-After within the retry budget. Longer throttle intervals defer to a future operator or scheduler. Neither provider response text nor token values are logged. Grant exchange, secret storage, and durable token refresh coordination belong to the later approved connection.
- The reconciliation prototype keeps one process-local mirror per configured organization. It stages a bounded page scan or deduplicated changed-ID reads, fetches source detail, and publishes the batch only on success. It preserves a known newer snapshot against an older explicit source timestamp and retains previous records when a list omits them. Date-only source revisions are observations with unresolved ordering. A failing batch preserves the prior snapshot and last-success time and records only a failure category and time. Overlap is rejected within the same instance. Full scans cap at 25 pages and changed hints at 5,000 inputs. A restart discards the prototype state.
- The mirror distinguishes draft, void/cancel, unemailed, unverified first send, and unmapped source salesperson. These are internal review states. Current source salesperson is an observation. Historical credit requires verified original revision evidence and a reviewed mapping. A future durable sale fact needs a unique organization/invoice key and separate historical rep, original subtotal, currency, first-send instant, evidence ID and policy version.
- The existing CRM flag and route authentication remain the only browser boundary. The dashboard links Monthly Sales and Monthly Invoices to an explanatory report status. It displays the first-email evidence gate and the absence of a successful sync. It publishes no invoice rows, report filters, source links, account details, or sales amounts. Commission and New Customers remain placeholders. A rep-supplied query parameter cannot select another rep's data. Team/company report scope requires real identities and explicit grants before a reporting API is introduced.
- No schema changes were made. A later persistent mirror must extend the approved storage architecture with additive source mappings, unique org/invoice keys, a timestamp/evidence audit and durable sync checkpoints. There are no migrations to roll back in this branch.

## First-email verification and backfill plan

1. Authorize a separate test task with a restricted, nonproduction organization and controlled recipients. Confirm actual invoice origin, accounts/API regions and version, configured business reporting timezone, plan limits, and what qualifies as success. Distinguish provider acceptance, failure and bounced delivery according to approved policy.
2. Compare Zoho history, Audit Trail, and available System Mails records against known send events and invoice revisions. Test manual single, bulk, automated, and any other intended path. Include mark-as-sent, reminder-only, draft, paid-before-email, failed send, bounce, repeated sends, month/timezone boundaries, and edits to amount or salesperson. Preserve sanitized fixtures and confirm a stable evidence ID, invoice join, offset or approved precision, and original subtotal/rep.
3. Confirm historical coverage and retention. Backfill only exact invoice joins with proven earliest success and attributable revision. An approved export or reviewed source-evidence import can cover proven gaps. A future controlled Zoho send workflow could establish prospective evidence where historical coverage is incomplete. If earliest success or attribution is unknown, keep that row unverified. Invoice creation, invoice date, current status, is_emailed, and sync time cannot supply the first-send timestamp.
4. Approve settlement and adjustments. Define void/deletion, credits, write-offs, refunds and reopened balances independently from warehouse release. Agree original subtotal versus later adjustments, adjustment period, currencies and FX policy. Validate source invoice links before exposing them. Only then implement rep-scoped reports and consistent Open/Closed/All invoice count and subtotal drilldowns.
5. Before any live read, approve account and organization allowlists, the read-only OAuth grant, a durable repository, protected token storage, quota budgets, cross-process leases, monitoring, and operator replay. Verify production role and salesperson mapping. Start with a limited read-only backfill and reconcile before publishing any figures.
